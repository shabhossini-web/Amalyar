# پشتیبان‌گیری و بازگردانی — راهنمای مالک

> پشتیبانی که هرگز بازگردانده نشده فقط یک فایل است. این‌جا هم **گرفتن** (خودکار، هر شب) هست و هم **تمرینِ بازگردانی**
> (ماهی یک‌بار، روی سرورِ دورریختنی). هر دو اسکریپت در `scripts/ops/` هستند و با Postgresِ واقعی در CI آزموده می‌شوند
> (`scripts/e2e/backup-drill.mjs`).

## ۱) چه چیزهایی باید پشتیبان داشته باشد — چهار چیز، نه یکی

| # | چیز | کجاست | اگر نباشد |
|---|---|---|---|
| ۱ | **دیتابیس‌ها** — مرکزی + یکی برای هر شرکت | Postgres (Coolify) | همه‌چیز رفته |
| ۲ | **نقش‌های Postgres** (رمزِ دیتابیسِ هر شرکت) | همان Postgres (`pg_dumpall --globals-only`) | دیتابیس‌ها برمی‌گردند ولی برنامه به هیچ‌کدام وصل نمی‌شود |
| ۳ | **پوشهٔ فایل‌ها** — عکس و مدارکِ بیماران | volume `ggdkvpdff3me1bzxqzhb2uud-amalyar-storage` روی `/app/storage` (Coolify ← amalyar-api ← Persistent Storage) | ردیف‌های مدارک می‌مانند ولی فایلشان نیست |
| ۴ | **رازها و متغیرها** — **همهٔ** متغیرهای هر دو اپِ Coolify (بک‌اند و فرانت)، نه فقط چند تا: `TENANT_DATABASE_ENCRYPTION_KEY`، `JWT_SECRET`، `CONTROL_DATABASE_URL`، `PROVISIONING_DATABASE_URL`، `MELI_API_KEY`، `MELI_FROM`، `CORS_ORIGINS`، `RP_ID`، `WEBAUTHN_ORIGINS`، `PORT`… | Coolify ← هر اپ ← Environment Variables | بدونِ کلیدِ رمزنگاری، نشانیِ دیتابیسِ شرکت‌ها (رمزشده در دیتابیسِ مرکزی) خوانده نمی‌شود؛ بقیه را باید از حافظه بازسازی کنی |

⚠️ **چهارمی را اسکریپت نمی‌گیرد و نباید هم بگیرد.** همهٔ متغیرهای هر دو اپ را یک‌بار از Coolify کپی کن و در یک **مدیرِ رمز**
(یا یک فایلِ رمزشدهٔ آفلاین) نگه دار — **نه کنارِ پشتیبان**؛ پشتیبانی که کلیدِ بازکردنش کنارش باشد محرمانه نیست. با هر تغییرِ
متغیرها دوباره کپی کن.

دو نکته که اسکریپت خودش رعایت می‌کند:
- **فهرستِ دیتابیس‌ها از خودِ Postgres خوانده می‌شود**، نه از فهرستی که دستی بنویسی — شرکتِ تازه خودکار پوشش داده می‌شود.
  دیتابیسِ پیش‌فرضِ `postgres` هم اگر جدولی دارد گرفته می‌شود: **در نصبِ فعلی دیتابیسِ مرکزی همان‌جاست** (پشتیبانِ اول
  بدونِ این قاعده هشت شرکت را گرفت و مرکزی را جا انداخت).
- **فایل‌ها بعد از دیتابیس‌ها** گرفته می‌شوند (با نامِ محتوا ذخیره‌اند)؛ پس هر فایلی که یک ردیفِ دامپ به آن ارجاع می‌دهد در
  آرشیو هست — مگر فایلی که درست میانِ دو گام پاک شده باشد. تمرینِ بازگردانی همین را برای هر شرکت جدا می‌سنجد.

## ۲) پانزده دقیقه تا اولین پشتیبانِ واقعی

همهٔ دستورها روی **میزبانِ سرور** (`62.60.214.40`) اجرا می‌شوند — همان‌جا که Docker و Coolify هستند، نه داخلِ کانتینر.
اگر SSH نداری: Coolify ← منوی کناریِ **Terminal** ← سرورِ `localhost` (نه Terminalِ خودِ اپ — آن داخلِ کانتینر است و Docker ندارد).

**گام ۱ — اسکریپت‌ها را روی سرور بگذار** (یک‌بار؛ بعد از هر تغییرِ اسکریپت در مخزن دوباره):

```bash
sudo mkdir -p /opt/amalyar-ops /var/backups/amalyar
sudo nano /opt/amalyar-ops/backup.sh          # محتوای scripts/ops/backup.sh را از گیت‌هاب (Raw) کپی و paste کن؛ Ctrl+O، Enter، Ctrl+X
sudo nano /opt/amalyar-ops/restore-drill.sh   # همین برای restore-drill.sh
sudo chmod +x /opt/amalyar-ops/*.sh
```

**گام ۲ — فایلِ تنظیمات** (یک‌بار). روی میزبانِ Coolify دو Postgres هست: دیتابیسِ خودِ Coolify (`coolify-db`) و دیتابیسِ
عمل‌یار. اسکریپت اولی را خودش کنار می‌گذارد، ولی نام‌ها را صریح بنویس تا cron هیچ‌وقت حدس نزند:

```bash
docker ps --format '{{.Names}}  {{.Image}}'   # نامِ کانتینرِ postgres:18 را بردار — نه coolify-db
openssl rand -hex 32                          # رمزِ پشتیبان: همین ۶۴ حرف را اول در مدیرِ رمز ذخیره کن
sudo nano /etc/amalyar-backup.env
```

و این چهار خط را بنویس (جای `<…>` را پر کن؛ Ctrl+O، Enter، Ctrl+X):

```
PG_CONTAINER=<نامِ کانتینرِ postgres:18>
STORAGE_VOLUME=ggdkvpdff3me1bzxqzhb2uud-amalyar-storage
BACKUP_PASSPHRASE='<همان ۶۴ حرفِ openssl rand>'
# RCLONE_REMOTE=arvan:amalyar-backups      ← بعد از بندِ ۳، علامتِ # را بردار
```

```bash
sudo chmod 600 /etc/amalyar-backup.env       # فقط root بخواند
```

هر دو اسکریپت این فایل را **خودشان** می‌خوانند — نه در خطِ cron، نه در خطِ فرمان، رمزی تایپ نمی‌شود (تاریخچهٔ شل و لاگِ sudo
خطِ فرمان را نگه می‌دارند). فایل **متنی** خوانده می‌شود: `$`، فاصله، `#` یا `;` در رمز همان‌طور می‌ماند و نقلِ قولِ دورش برداشته
می‌شود؛ کلیدِ غلط‌تایپی (مثلاً `PG_CONTAINR`) خطای روشن می‌دهد، نه این‌که بی‌صدا نادیده گرفته شود.

**گام ۳ — اولین پشتیبان** (باید «تمام شد» بدهد؛ هر خطا فارسی و روشن است):

```bash
sudo /opt/amalyar-ops/backup.sh
```

خروجیِ درست چیزی شبیهِ این است (نام‌ها و حجم‌ها فرق می‌کند):

```
پشتیبان‌گیری — Postgres 18.0 → /var/backups/amalyar/20261008T023001Z
  ✔ نقش‌ها
  ✔ amalyar_control (9 MB)
  ✔ amalyar_dr_gorji (41 MB)
  ✔ فایل‌ها (1523 فایل، 612M)
  ✔ چکیده‌ها و خلاصه
تمام شد: /var/backups/amalyar/20261008T023001Z
```

**گام ۴ — تمرینِ بازگردانی، همان لحظه** (تا مطمئن شوی پشتیبان با همین رمز واقعاً برمی‌گردد):

```bash
sudo /opt/amalyar-ops/restore-drill.sh
```

یک کانتینرِ Postgresِ تازه و موقت می‌سازد، پشتیبان را آن‌جا برمی‌گرداند، می‌سنجد و پاکش می‌کند — **به دیتابیسِ زنده دست نمی‌زند.**
رمز را از همان فایلِ گامِ ۲ می‌خواند. خروجیِ درست با «**تمرین موفق**» تمام می‌شود و یک جدولِ شمارِ ردیف‌ها دارد؛ شمارِ بیماران و
مراجعاتِ هر شرکت را با آنچه در برنامه می‌بینی تطبیق بده. «تمرین موفق با N هشدار» یعنی برگشت ولی سطرهای «!» را بخوان.
اگر «تمرین ناموفق» گفت، **آن پشتیبان را قابلِ اتکا نشمار** و متنِ خروجی را برای من بفرست.

**گام ۵ — زمان‌بندیِ شبانه** (ساعتِ ۰۲:۳۰ به وقتِ سرور) — فقط همین یک خط؛ تنظیمات از فایلِ گامِ ۲ می‌آید:

```bash
sudo crontab -e
# این یک خط را اضافه کن:
30 2 * * * /opt/amalyar-ops/backup.sh >> /var/log/amalyar-backup.log 2>&1
```

**هفته‌ای یک نگاه — پشتیبانِ دیشب واقعاً گرفته شد؟** (cron اگر بیفتد به کسی خبر نمی‌دهد):

```bash
cat /var/backups/amalyar/LAST_SUCCESS          # تاریخِ آخرین پشتیبانِ موفق — باید دیشب باشد
ls /var/backups/amalyar/LAST_UPLOAD_FAILED     # «No such file» یعنی آپلودِ بیرونی هم موفق بوده
tail -n 20 /var/log/amalyar-backup.log         # اگر تاریخ کهنه است، علت این‌جاست
```

دیسکِ سرور را پایش کن: هر شب یک پوشه (حجمِ دیتابیس‌ها + فایل‌ها) و `RETENTION_DAYS=14` روز نگه می‌دارد (دست‌کم سه پوشهٔ تازه همیشه می‌ماند).

## ۳) بیرونِ سرور (ضروری)

پشتیبانی که روی همان دیسکِ سرور است، با خرابیِ آن سرور (یا حذفِ VPS) همراهش می‌رود. حتماً یک **نسخهٔ بیرونی** هم بگیر:

1. یک سرویسِ ذخیره‌سازیِ سازگار با S3 (مثلاً **Object Storage آروان**) بساز و یک bucket خصوصی (مثلاً `amalyar-backups`) + یک جفت کلیدِ دسترسی.
2. روی سرور `rclone` نصب کن (`curl https://rclone.org/install.sh | sudo bash`) و یک remote بساز: `sudo rclone config` ← `n` ← نام `arvan` ←
   نوعِ `s3` ← provider `Other` ← کلیدها ← **endpoint** را از پنلِ همان سرویس بردار.
3. در `/etc/amalyar-backup.env` جلوی خطِ `RCLONE_REMOTE` علامتِ `#` را بردار (`sudo nano /etc/amalyar-backup.env`).

با `BACKUP_PASSPHRASE` همهٔ فایل‌ها با AES-256 رمز می‌شوند (پسوندِ `.enc`) و **هیچ دامپِ بی‌رمزی روی دیسک نمی‌ماند**؛ با `RCLONE_REMOTE` همان
پوشه پس از موفقیت بیرون می‌رود. اگر آپلود نشد (شبکه، کلید)، پشتیبانِ محلی سالم می‌ماند، کنارش `UPLOAD_FAILED` و کنارِ `LATEST` فایلِ
`LAST_UPLOAD_FAILED` می‌نشیند و کدِ خروجی `3` است. ⚠️ **رمز را در مدیرِ رمز نگه دار** — بدونِ آن پشتیبانِ رمزشده برنمی‌گردد.

> لایهٔ دومِ اختیاری: Coolify ← Postgres ← **Backups** هم دامپِ زمان‌بندی‌شده با مقصدِ S3 دارد. اگر روشنش می‌کنی، مطمئن شو گزینهٔ «همهٔ
> دیتابیس‌ها» (dump all) روشن است وگرنه فقط دیتابیسِ پیش‌فرض را می‌گیرد و شرکت‌ها بیرون می‌مانند. این لایه جایگزینِ اسکریپت نیست: نقش‌ها، فایل‌ها و
> تمرینِ بازگردانی را ندارد.

## ۴) تمرینِ بازگردانی — ماهی یک‌بار

```bash
sudo /opt/amalyar-ops/restore-drill.sh                       # آخرین پشتیبان (رمز از /etc/amalyar-backup.env)
sudo /opt/amalyar-ops/restore-drill.sh 20261008T023001Z      # یکی از قبلی‌ها
```

آنچه سنجیده می‌شود (هر کدام قرمز شود، تمرین ناموفق است): چکیدهٔ فایل‌ها · برگشتنِ **همهٔ** نقش‌ها، و نقشِ هر شرکت با اجازهٔ ورود و رمز ·
برگشتنِ هر دیتابیس بدونِ خطا · دیتابیسِ مرکزی و دیتابیسِ **هر شرکتِ فعال با نامِ خودش** (`amalyar_<شناسه>`) و migration ·
وجودِ هر فایلی که دیتابیسِ یک شرکت به آن ارجاع می‌دهد (مدرک، اثباتِ تحویل، عکسِ سایت، سربرگ) **در پوشهٔ همان شرکت**.

**فایلی که از قبل روی سرور نبود** (مثلاً مدارکی که پیش از ماندگارشدنِ پوشهٔ فایل‌ها با یک دیپلوی پاک شدند — اولین تمرینِ
واقعی ۲۴ مدرکِ آپلودشده پیش از ۱۴۰۵/۰۷/۰۱ را این‌طور پیدا کرد) شکستِ پشتیبان نیست: `backup.sh` همان لحظه آن را می‌گوید
(«! N فایلِ ارجاع‌شده همین الان روی سرور نیست» با شمارِ هر شرکت) و در `MISSING_FILES.txt` ثبت می‌کند، و تمرین آن را
«هشدار» می‌گوید و با «تمرین موفق با N هشدار» تمام می‌شود. «ناموفق» فقط برای فایلی است که روی سرور بود ولی در پشتیبان نیست.
خودِ برنامه هم مدرکِ بی‌فایل را می‌شناسد (ساعتی، `detectLostFiles`): ردیفش در پرونده قرمز می‌شود با «آپلودِ دوباره»، منشیِ همان شرکت
در «کارهای من» کارِ «دوباره آپلود کنید» می‌گیرد و پنلِ پلتفرم کنارِ شرکت فقط شمار را نشان می‌دهد — پس عددِ `MISSING_FILES.txt` باید با
همان شمار بخواند.
در پایان **زمانِ بازگردانی** را می‌گوید — همان «شبِ فاجعه چقدر طول می‌کشد؟». تاریخ و نتیجه را در `STATUS.md` یادداشت کن.

برای پشتیبانی که از بیرونِ سرور برمی‌گردانی: اول `rclone copy arvan:amalyar-backups/<پوشه> /var/backups/amalyar/<پوشه>` و بعد همان دستور.

## ۵) بازگردانیِ واقعی (فاجعه) — ترتیبِ کار

۱. سرورِ تازه + Coolify + یک منبعِ Postgres **با همان نسخه** (`postgres:18-alpine`)؛ هنوز برنامه را روشن نکن.
۲. متغیرهای هر دو اپ را از مدیرِ رمز در Coolify بگذار (`TENANT_DATABASE_ENCRYPTION_KEY` **دقیقاً همان** مقدارِ قبلی؛ `CONTROL_DATABASE_URL`
   و `PROVISIONING_DATABASE_URL` با **نامِ میزبانِ Postgresِ تازه**).
۳. پشتیبان را (از بیرونِ سرور) بیاور. اگر رمزشده است، رمز را در یک فایلِ فقط-root بگذار (`sudo nano /root/backup-pass` ← فقط همان ۶۴ حرف
   ← `sudo chmod 600 /root/backup-pass`) و هر فایل را باز کن:
   `sudo openssl enc -d -aes-256-cbc -pbkdf2 -pass file:/root/backup-pass -in X.enc -out X`
۴. داخلِ کانتینرِ Postgres، **اول نقش‌ها، بعد هر دیتابیس**:
   ```bash
   docker exec -i <pg> psql -U postgres -d postgres < globals.sql
   docker exec -i <pg> pg_restore -U postgres -d postgres < postgres.dump                   # دیتابیسِ مرکزی — بی‌‌--create
   docker exec -i <pg> pg_restore -U postgres -d postgres --create < amalyar_dr_gorji.dump  # برای هر فایلِ .dumpِ دیگر
   ```
   (خطای «role postgres already exists» در مرحلهٔ نقش‌ها عادی است.) **دیتابیسِ مرکزیِ نصبِ فعلی همان دیتابیسِ پیش‌فرضِ
   `postgres` است** (Coolify آن را «Initial DB» ساخت)؛ چون روی هر سروری از قبل هست، بی‌`--create` در همان برمی‌گردد.
۵. فایل‌ها را در volume بریز: `docker run --rm -v <نامِ volume>:/data -v $PWD:/b alpine tar -xzf /b/storage.tar.gz -C /data` (Coolify جلوی نامِ volume شناسهٔ اپ را می‌گذارد، مثلِ `ggdkvpdff3me1bzxqzhb2uud-amalyar-storage`).
۶. بک‌اند را Deploy کن. **نشانیِ دیتابیسِ شرکت‌ها هنوز به Postgresِ سرورِ قبلی اشاره می‌کند** (رمزشده در دیتابیسِ مرکزی ساخته شده
   بود)؛ پس دیتابیسِ مرکزی کار می‌کند ولی هیچ شرکتی باز نمی‌شود. Coolify ← بک‌اند (amalyar-api) ← **Terminal**:
   ```bash
   node dist/scripts/rehost-tenants.js            # فقط نشان می‌دهد؛ برای هر شرکت باید «✔ … وصل شد» بدهد
   node dist/scripts/rehost-tenants.js --apply    # می‌نویسد — فقط شرکت‌هایی که با نشانیِ تازه واقعاً وصل شدند
   ```
   میزبانِ تازه را از `PROVISIONING_DATABASE_URL` برمی‌دارد (یا `TARGET_DATABASE_HOST=میزبان:درگاه`). «رمزگشایی نشد» یعنی
   `TENANT_DATABASE_ENCRYPTION_KEY` همان مقدارِ قبلی نیست. بعد بک‌اند را یک‌بار **Restart** کن.
۷. فرانت را Deploy کن. در `/platform-admin` ← «آمادگیِ سامانه»: پیامک سبز؛ **فایل‌ها کهربایی** («ماندگاری ثابت نشده») — درست است، چون
   اثباتِ ماندگاری عمداً در پشتیبان نیست (بندِ ۶)؛ یک Redeployِ دیگرِ بک‌اند سبزش می‌کند. درستیِ بازگردانی را با باز کردنِ هر شرکت و
   دیدنِ چند پرونده و **مدرک** بسنج.

تمرینِ ماهانه گام‌های ۳ تا ۵ را آزموده است؛ گامِ ۶ (نشانیِ شرکت‌ها) فقط روی سرورِ تازه معنا دارد و تمرین آن را نمی‌آزماید — پس
خروجیِ «فقط نشان می‌دهد»ش را پیش از `--apply` بخوان.

## ۶) ماندگاریِ فایل‌های آپلودی (بندِ ۱) — برنامه خودش ثابتش می‌کند

بالای `/platform-admin` نوارِ «**آمادگیِ سامانه**» است. چیپِ «فایل‌ها»:

| چیپ | یعنی | کار |
|---|---|---|
| سبز «ماندگار» | دو کانتینرِ متفاوت (دو دیپلوی) روی همین پوشه نوشته‌اند — **اثبات شد** | هیچ |
| کهربایی «ماندگاری ثابت نشده» | پوشه روی volume جداست ولی هنوز دیپلوییِ دوم نشده | یک دیپلوی (Redeploy) بزن؛ سبز می‌شود |
| قرمز «روی volume نیست» | پوشهٔ فایل‌ها روی لایهٔ موقتِ کانتینر است — **با دیپلوی بعدی همهٔ فایل‌ها پاک می‌شود** | Coolify ← بک‌اند ← **Storages** ← volumeای با مقصدِ `/app/storage` (نامِ دلخواه، مثلاً `amalyar-storage`) و متغیرِ `STORAGE_ROOT` را **خالی** بگذار |
| قرمز «قابل نوشتن نیست» | آپلودها شکست می‌خورند | مجوزِ volume؛ لاگِ بک‌اند |

برنامه در هر بوت نامِ کانتینر را در `/app/storage/.ledger/containers.json` ثبت می‌کند (کنارِ خودِ فایل‌ها، نه در دیتابیس)؛ پس اگر روزی
volume عوض یا خالی شود، اثباتِ ماندگاری هم با آن صفر می‌شود و چیپ دوباره کهربایی می‌شود. همین دفتر **عمداً در پشتیبان نیست**:
بعد از بازگردانی روی volumeِ تازه، چیپ تا دیپلویِ بعدی کهربایی می‌ماند — اثباتِ volumeِ قبلی به volumeِ جدید ارث نمی‌رسد.

## ۷) چک‌لیستِ پیش از اولین مشتریِ پولی

- [ ] چیپِ «فایل‌ها» سبز (بند ۶)
- [ ] چیپِ «پیامک» سبز + یک پیامکِ واقعی به گوشیِ خودت (پرونده ← «پیامکِ لینک»)
- [ ] `/etc/amalyar-backup.env` با `PG_CONTAINER`، `STORAGE_VOLUME` و رمز (رمز اول در مدیرِ رمز)
- [ ] `backup.sh` دستی موفق + `restore-drill.sh` «تمرین موفق» + زمانِ بازگردانی یادداشت‌شده
- [ ] cron شبانه + فردای آن `cat /var/backups/amalyar/LAST_SUCCESS` تاریخِ دیشب را نشان داد
- [ ] نسخهٔ بیرونیِ رمزشده (`RCLONE_REMOTE`) + همهٔ متغیرهای هر دو اپ در مدیرِ رمز
- [ ] یک تمرینِ بازگردانی در تقویم (ماهی یک‌بار) و نگاهِ هفتگی به `LAST_SUCCESS`

## چرا این‌طور (برای ایجنت‌های بعدی)

- `backup.sh` به `pg_dumpall --globals-only` + `pg_dump -Fc` به‌ازای هر دیتابیس + tarِ volume متکی است؛ **نقش‌ها لازم‌اند** چون دیتابیسِ هر شرکت
  مالکِ یک نقشِ جدا دارد و `pg_restore --create` با همان مالک می‌سازد.
- تمرین عمداً **هرگز** روی Postgresِ زنده نمی‌دود: حالتِ Docker کانتینرِ تازه می‌سازد و حالتِ محلی (`DRILL_LOCAL=yes`) سرورِ غیرِ‌خالی را رد می‌کند.
- فایلِ تنظیمات **متنی** خوانده می‌شود، نه با `source`: دستورِ قبلیِ همین سند فایل را با heredocِ بی‌نقل می‌ساخت و cron آن را `.` می‌کرد،
  پس `$`/`` ` `` هنگامِ نوشتن و فاصله/`#`/`;` هنگامِ خواندن رمز را عوض می‌کردند و پشتیبان با رمزِ مدیرِ رمز باز نمی‌شد.
- نشانیِ دیتابیسِ هر شرکت میزبانِ Postgres را در خود دارد (`database_url_encrypted`)؛ بازگردانی روی سرورِ تازه بدونِ
  `rehost-tenants` همهٔ شرکت‌ها را به سرورِ مرده وصل می‌کند.
- نمایشِ «سبز»ِ ساختگی برای پشتیبان در پنلِ پلتفرم ممنوع است؛ برنامه از پشتیبانِ بیرونی خبر ندارد و چیپِ «پشتیبان» عمداً «خارج از برنامه» می‌گوید.
- هر تغییر در دو اسکریپت باید `scripts/e2e/backup-drill.mjs` را سبز نگه دارد (CI).
