# همکاری Codex و Claude روی دستیارهای عملیار

وضعیت: تقسیم پیشنهادی کار؛ تأیید دریافت یا پذیرش تسک توسط Claude ادعا نمی‌شود. این سند مستقیماً به سرویس دیگری ارسال نشده است و از طریق مخزن مشترک قابل خواندن خواهد بود.

مرجع همکاری، [AGENTS.md](../../AGENTS.md) و مرجع قواعد محصول، [CLAUDE.md](../../CLAUDE.md) است. این سند آن‌ها را جایگزین نمی‌کند.

## این بسته دقیقاً چه چیزی دارد

- طراحی مدیریت نسخه و اختیار ایجنت‌ها.
- JSON Schema پیشنهادی تعریف ایجنت و دو نمونه، با تصریح جدایی ساختار و مجوز واقعی.
- طرح اولیه معماری گفتگوهای قبلی، برای جلوگیری از گم‌شدن تصمیم‌ها.
- به‌روزرسانی فقط فایل هماهنگی `.sync/gpt.md`؛ فایل‌های Claude و قراردادهای اجرایی فعلی تغییر نمی‌کنند.

## تقسیم پیشنهادی پس از این بسته

| مسیر کار | مسئول پیشنهادی | وابستگی |
|---|---|---|
| هسته تسک و مدیریت نسخه، رجیستری ابزار و اختیار واگذاری | Codex | تثبیت قرارداد کوچک HTTP و data model |
| صفحه مرکز فرمان و مدیریت ایجنت، نمایش تفاوت و نتیجه اجرا | Claude، در صورت پذیرفتن این محدوده | نمونه پاسخ و قرارداد همان برش؛ امکان شروع با fixture |
| ابزارهای حسابداری و انبار | یک مالک مشخص برای هر برش | هسته مجوز و تثبیت منشأ مصرف کارشناس |
| فرم و گردش‌کار | یک مالک برای اتصال backend و یک مالک UI | ابزارهای منتشرشده، نسخه فرم و رویدادهای معتبر |
| اتصال توسعه کد و Git | مسیر جدا در سطح پلتفرم | محیط مستقل، ابزارهای محدود و گیت انتشار |

هر طرف پیش از شروع، فقط مسیرهایی را که واقعاً می‌نویسد در فایل `.sync` خودش فعال کند. جدول بالا هیچ مسیر کدی را از طرف Claude claim نمی‌کند. در زمان بررسی، claimهای روی main حالت idle داشتند؛ این مشاهده به معنی نبود تغییر محلی یا تأیید تقسیم کار نیست.

## اولین برش مشترک

«مدیر، فهرست ایجنت‌ها را ببیند؛ با زبان طبیعی یا فرم، یک پیش‌نویس ایجنت بسازد؛ محدودیت و تفاوتش با نسخه فعال را ببیند؛ بدون اجرای ابزار مالی آن را ذخیره کند.»

این برش باید طبق قانون ماژول جدید در CLAUDE.md، feature/permission، API، صفحه و launcher و آزمون end-to-end کامل داشته باشد. ایجاد چند فایل backend به‌تنهایی تکمیل ماژول محسوب نمی‌شود.

Codex و Claude پیش از کدنویسی یکسان روی این موارد توافق کنند: شکل فهرست و نسخه، خطاهای فارسی، وضعیت تسک، مرجع مجوز، شیوه احراز و نمونه پاسخ. برای آشنایی frontend با backend تازه، fixture با برچسب روشن استفاده شود؛ UI نباید وجود endpoint پیاده‌نشده را به کاربر واقعی القا کند.

## جلوگیری از تداخل

۱. ابتدای کار main، ده کامیت آخر، PRهای باز و `.sync/*.md` خوانده شود. ادعای سند درباره «کار باقی‌مانده» با کد سنجیده شود.

۲. شاخه‌های کوتاه‌عمر و برش‌های کوچک استفاده شوند. فایل مشترک `schema.prisma`، رجیستری دسترسی، App، Launcher و STATUS برای هر برش یک نویسنده مشخص داشته باشند. تغییر به فایل پرتنش طبق قاعده append-only مخزن باشد.

۳. هماهنگی صرفاً با دیدن نام شاخه کافی نیست؛ قبل از نوشتن مسیر موردنظر، claim فعال همان مسیر بررسی شود. دسترسی مشترک به مخزن به معنی مشاهده خودکار گفت‌وگو یا تغییرات ذخیره‌نشده طرف دیگر نیست.

۴. تغییر قرارداد HTTP، session، helper تست یا کلاس عمومی در بخش «قراردادهایی که شکستم» فایل claim همان نویسنده ثبت شود. نسخه قرارداد و نمونه‌ها نیز در همان بسته تغییر کنند.

۵. پیش از push، HEAD شاخه و main دوباره خوانده شوند؛ `pr-health` ممکن است شاخه را روی GitHub جلو برده باشد. force-push برای جبران این اختلاف استفاده نشود.

۶. build هر دو سمت و سناریوهای مرتبط طبق قانون ۱۲ اجرا شوند. این بسته سندی مسیر UI/API را تغییر نمی‌دهد؛ سنجه مرتبط آن اعتبار schema، نمونه‌ها و پروتکل claim است. آزمون runtime ایجنت هنوز موضوع این بسته نیست.

۷. draft یا hold مانع automerge موجود است. پیش‌نویس بودن این بسته یعنی قرارداد طراحی قابل بازبینی است و ماژول اجرایی هنوز ساخته نشده؛ به معنی درخواست مجوز دوباره برای استقرارهای قبلاً مجاز نیست. هنگام اتمام یک برش اجرایی و عبور از گیت‌ها، سیاست انتشار موجود مخزن رعایت شود.

## قراردادهای حفظ‌شده

- کوکی HttpOnly و CSRF و helper موجود تست مرورگر.
- tenant فقط از context معتبر سرور، با دیتابیس جدا برای هر شرکت.
- پول تومان صحیح و محاسبات مالی سمت سرور.
- مصرف واقعی، اقلام فاکتور و پرداخت‌های ثبت‌شده مستقل از هم.
- مجوزهای ایجنت در سرویس کنترل می‌شوند؛ متن یا manifest مجوز ایجاد نمی‌کند.
- تغییر نسخه فرم/ایجنت، تاریخچه و اجراهای قبلی را بی‌صدا بازنویسی نمی‌کند.
