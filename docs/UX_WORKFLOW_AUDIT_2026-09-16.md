**نسبت با گزارشِ ChatGPT («گزارش بررسی مسیرها و UX عملیار — ۲۰۲۶/۰۹/۱۶»):** این سند آن گزارش را **جایگزین نمی‌کند**؛ آن را راستی‌آزمایی می‌کند، یافته‌های تازه اضافه می‌کند، چارچوبِ محصولی/برند می‌دهد و در پایان یک **تقسیم‌بندیِ اجرایی** می‌سازد که هر دو گزارش را پوشش می‌دهد. برای شروعِ کار خواندنِ همین سند کافی است؛ هر یافتهٔ ChatGPT این‌جا با شمارهٔ خودش (D01…D10) آمده.

## ۰. نتیجه در یک نگاه

1. **گزارشِ ChatGPT درست است.** هر ده یافته‌اش (D01…D10) در کد تأیید شد — با شمارهٔ خط در بخش ۲. چهار باگِ تازه هم پیدا شد که آن گزارش ندیده بود (N1…N4)؛ یکی از آن‌ها (N1) داده‌ای را که امروز داریم می‌تواند بی‌صدا نابود کند.
2. **ریشهٔ مشترک یک چیز است: واحدِ محصول «ماژول» است، نه «کار».** ۲۲ کاشی ساخته‌ایم که هرکدام به‌تنهایی درست کار می‌کنند، ولی هیچ‌جا نمی‌گوید «الان چه کسی باید چه کاری برای کدام بیمار تا کِی انجام دهد». این را کاربر در سرش نگه می‌دارد — یعنی همان منشی‌ای که هدفِ محصول حذفِ نیاز به اوست.
3. **لایهٔ «کار» همان بسترِ ایجنتیک است، نه یک مرحلهٔ قبل از آن.** ایجنت فقط وقتی امن و مفید است که کار تایپ‌دار باشد، اقدامش idempotent باشد، خروجی‌اش قابلِ ممیزی باشد و حلقهٔ تأییدِ انسانی داشته باشد. اگر هر نوعِ کار از روزِ اول یک فیلدِ «مجری» بگیرد (انسان ← پیشنهادِ دستیار ← خودکار با تأیید ← خودکار با استثنا)، «ایجنتیک‌شدن» یعنی بالابردنِ همین نردبان به‌ازای هر نوعِ کار و هر شرکت — نه بازنویسی و نه یک «مرکزِ ایجنت‌ها»ی جدا.
4. **اهرمِ کاهشِ پرسنل دو چیز است:** (الف) سامانه خودش پیگیری کند — نتیجه، نوبت، یادآوری، آماده‌سازیِ ویزیت؛ (ب) بیمار خودش کارش را انجام دهد — نوبت، پرداخت، آپلود، پاسخ — از **یک لینکِ واحد**. امروز بیمار شش نوع لینکِ جدا می‌گیرد و پرتالش فقط تاریخچه نشان می‌دهد؛ کانالِ ما هم فقط پیامک است.
5. **برندِ «هوشمند عمل کن» باید در اپ نشان داده شود، نه نوشته.** سه لحظهٔ امضایی پیشنهاد می‌شود (خلاصهٔ صبح، کارتِ آماده‌سازیِ ویزیت، پیگیریِ خودکارِ نتیجه)؛ هیروی برند از صفحهٔ روزانه به لاگین/لندینگ برود؛ تمِ روشنِ بالینی به‌عنوانِ نسخهٔ دومِ همان توکن‌ها اضافه شود.
6. **ترتیبِ اجرا:** اصلاح‌های سریع ∥ صحت و پیوستگی ← لایهٔ کار + صفحهٔ «امروز» ← سه سطحِ رابط ← مسیرِ درمان/راه‌اندازی/سنجش ∥ دستیار درونِ کارها. بخش ۵ همین را به ۴۰ بستهٔ قابلِ واگذاری تقسیم کرده است.

## ۱. روش

- سه بررسیِ موازی روی همان کامیت، فقط‌خواندنی، بدون تغییرِ محصول:
  1. **راستی‌آزماییِ D01…D10** با بازکردنِ کدِ هر یافته و ثبتِ `file:line` (به‌علاوهٔ دو موردِ اضافه: هم‌زمانیِ `startVisit` و idempotencyِ یادآوری).
  2. **موجودیِ UX به‌ازای نقش**: لانچر و کاشی‌های هر سطح، داشبورد و شیتِ ویزیت، پرونده، شش سطحِ بیمار، سطوحِ کارکنان (کارشناس/جراح/CRM/یادآوری/تقویم/برنامه/چینش)، ورودِ تکراری، راه‌اندازیِ شرکتِ تازه.
  3. **موجودیِ زیرساختِ اتوماسیون و AI**: ماژولِ AI، خطِ لولهٔ یادآوری/پیامک، primitiveهای رویداد/کار، تعریفِ مسیر، کانال‌های بیمار، گزارش‌ها، سطحِ پیکربندیِ per-tenant.
- هفت اسکرین‌شاتِ گزارشِ ChatGPT مستقلاً دیده شد و سندهای `STATUS.md`، `ROADMAP.md`، `docs/BOOKING.md`، `docs/INTAKE_WORKFLOW_REVIEW_2026-09-08.md`، `docs/PROFILE_WORKFLOWS_2026-09-09.md` خوانده شد تا چیزی که قبلاً انجام شده دوباره پیشنهاد نشود.
- محدودیت‌ها همان محدودیت‌های گزارشِ ChatGPT است: دادهٔ واقعیِ هیچ شرکتی خوانده نشد، آزمونِ کاربرِ واقعی انجام نشد، برآوردِ زمانی بدونِ sizing تیم قابلِ اتکا نیست.

## ۴. تجربهٔ هدف

### ۴.۱ مدلِ «کار» — بسترِ مشترکِ رابط و ایجنت

```
WorkItem {
  id, type            // review_result · call_patient · confirm_appointment · collect_payment ·
                      // approve_intake · complete_report · confirm_usage · issue_invoice ·
                      // fill_form · upload_result · pick_slot · resend_sms · …
  subject             // ارجاعِ صریح: {patientId?, visitId?, appointmentId?, orderId?, submissionId?, invoiceId?}
                      // هرگز تطبیقِ نام/تاریخ
  owner               // {role?} | {accountId?} | 'patient' | 'system'
  dueAt, priority
  state               // open · blocked · done · cancelled · expired
  performer           // human · assistant_suggests · assistant_auto_approve · assistant_auto
  outcome Json        // خروجیِ لازم (مثلاً reviewDecision, callResult, nextDue)
  blockedReason, sourceEventId, idempotencyKey @unique, createdBy, auditRef
}
DomainEvent {         // outbox: هر نوشتنِ حساس یک رویداد در همان تراکنش
  id, type, subjectRefs, payload, at, actorId, processedAt?
}
```

- **نردبانِ مجری** (به‌ازای هر `type` و هر شرکت، از تنظیمات): انسان ← دستیار **پیشنهاد** می‌دهد و انسان یک‌کلیکی تأیید می‌کند ← دستیار **انجام می‌دهد** و انسان فقط استثناها را می‌بیند. همین یک فیلد، مسیرِ ایجنتیک‌شدن است.
- **قواعد:** هر کار ارجاعِ صریح دارد؛ هر اقدام idempotencyKey دارد؛ هر انجام/رد در `AuditEvent` ثبت می‌شود؛ «ارسال»، «تحویل»، «مشاهده»، «انجامِ کار» چهار رویدادِ جدا هستند؛ کارِ بی‌مسئول و رویدادِ بی‌کار در «نمای استثنا»ی مدیر می‌نشیند.
- **چرا مدلِ جدا و نه ستون روی Reminder:** یادآوری «پیام» است؛ کار «تعهد با مسئول و مهلت» است. یکی‌گرفتنشان همان ابهامی است که «ارسال شد = انجام شد» را می‌سازد.

کاشی‌های امروز به «همهٔ ابزارها» (کشو/سایدبار) می‌روند؛ چیزی حذف نمی‌شود.

### ۴.۳ پروندهٔ زنده (به‌جای فرمِ ویرایش به‌عنوانِ خلاصه)

1. **کارتِ هویت** (نام، کد، سن، تلفن، حساسیت با نشانِ قرمز، بیمه) — فقط‌خواندنی، «ویرایش» یک اقدام است.
2. **نوارِ «الان کجاییم»** — مرحلهٔ فعلیِ دوره، چه چیزی کامل شده، چه چیزی مانده.
3. **کارتِ «کارِ بعدی»** — مسئول، موعد، دکمهٔ اصلی، مانع (اگر هست).
4. **خطِ زمان** — مراجعه‌ها، نتایج (با وضعیتِ بررسی)، فرم‌ها، پیام‌ها، نوبت‌ها — همه کلیک‌پذیر.
5. **اقدام‌ها** همیشه در دسترس: مراجعهٔ جدید، نوبت، ارسال فرم/لینک، پیام. تب‌ها (مدارک/شرح‌ها/مالی) ثانویه می‌شوند.

### ۴.۴ فضای کارِ ویزیت

- **پیش از ویزیت:** کارتِ آماده‌سازیِ خودکار (آخرین شرح‌ها، نتایجِ در انتظار، حساسیت‌ها، ماندهٔ مالی).
- **حینِ ویزیت:** شرحِ ساختاریافته بر اساسِ نقش (فرم‌ساز)، سفارش‌ها **پیش از ذخیره** (مراجعهٔ پیش‌نویس)، تصمیم‌ها.
- **پس از ویزیت:** قدمِ بعدی به‌صورتِ یک کار — نوبت + پیامِ مراقبت + فرمِ پیگیری — از همین‌جا، با پیش‌نمایشِ اثر.
- هویتِ ثابت بالا؛ بخش‌ها collapsible؛ ذخیرهٔ خودکار.

### ۴.۵ میزِ پذیرشِ روز

ستون‌های **نوبت‌دار / حاضر / در ویزیت / تمام‌شده / غایب**؛ «رسید» با شماره یا QR؛ نوبتِ حضوری در دو کلیک؛ چیپِ پرداخت؛ بعد از پایانِ ویزیت **برگشت به میز**، نه به داشبورد. سطحِ پیش‌فرضِ دسترسی برای منشی (۲).

### ۴.۶ لینکِ واحدِ بیمار

`/p/:token` = «کارهای من» (فرمِ باز، نتیجهٔ درخواستی، انتخابِ زمان، پرداخت) + نوبت‌ها + مدارک + پیام‌ها. `/f`، `/o`، `/v`، `/s` می‌مانند ولی به‌عنوانِ deep-link داخلِ همان پرتال باز می‌شوند. آپلودِ عکس/PDF روی نتیجه؛ پیش‌نویسِ per-page؛ لینک‌های کلیک‌پذیر؛ تاریخِ توصیه‌شده و نوبتِ قطعیِ **یک مرحله** در یک کارت (دو نوبتِ واقعیِ مستقل ادغام نمی‌شوند). کانالِ دوم (بله/روبیکا) بعد از W3.

### ۴.۷ فرم‌ساز

ردیفِ فشردهٔ هر فیلد (برچسب، نوع، اجباری) + **پنلِ کناری** برای تنظیماتِ همان فیلد + **ماتریسِ نقش‌ها یک‌جا** بالای فرم (فیلد × نقش) به‌جای تکرار در هر ردیف + پیش‌نمایشِ زنده. مسیرساز (W4) از همین فرم‌ها می‌خورد؛ فرم‌سازِ دومی ساخته نمی‌شود.

### ۴.۸ پوسته، جستجو، اعلان، تم، آیکون

نوارِ بالای ثابت روی همهٔ صفحاتِ `/app`: نشانِ کوچک + نامِ شرکت + جستجوی سراسریِ بیمار (⌘K / کلیدِ `/`) + زنگِ اعلان (از WorkItem) + `ProfileMenu`. لینکِ بازگشتِ یکسان. آیکونِ یکتا. تمِ روشنِ بالینی + سوییچ + چگالیِ فشرده/عادی. Escape و focus-trap در primitiveِ مودال؛ کلیدهای جهت در تب‌ها.

## ۶. سنجه‌ها و سناریوهای پذیرش

سنجه‌های گزارشِ ChatGPT (انجامِ مستقل، بارِ جابه‌جایی، پیوستگی، پاسخ و رسیدگی، بازیابی، اطلاع‌رسانی) پذیرفته می‌شود. دو چیز اضافه می‌شود:

**ابزارِ اندازه‌گیری** — `DomainEvent` (W2.1) هم‌زمان منبعِ analytics است؛ بدونِ آن هیچ عددِ قبل/بعدی نداریم. اولین کارِ W2.1 همین است، نه آخرین.

**اهدافِ عددیِ پیشنهادی** (پس از اندازه‌گیریِ پایه بازبینی شوند):

| سنجه | امروز (از کد) | هدف |
|---|---|---|
| کلیک از خانه تا «کارِ بعدیِ من» | ۲–۴ صفحه، بدونِ نشانه | ≤ ۱ (روی صفحهٔ امروز) |
| کلیک به‌ازای بیمارِ رسیده تا شروعِ ویزیت و برگشت | ~۶ + فرم | ≤ ۳ |
| ورودِ دوبارهٔ هویت/جراح/بیمارستان در یک فرایند | ۲ بار (ثبت‌نام ← تأیید) | ۰ |
| لینک‌های جداگانه‌ای که بیمار در یک دوره می‌گیرد | تا ۶ | ۱ (+ deep-link) |
| پیگیریِ ثبت‌شده ولی گزارش‌شده به‌عنوانِ «انجام‌نشده» | هر عملِ از‌پیش‌برنامه‌ریزی‌شده (D01) | ۰ |
| نتیجهٔ دریافت‌شده بدونِ وضعیتِ بررسی | ۱۰۰٪ | ۰ |
| پیامکِ `uncertain` بدونِ رسیدگی > ۱ ساعت | نامحدود | ۰ |
| تأییدِ ثبت‌نامِ نیمه‌کاره پس از خطا | ممکن، غیرقابلِ کشف | ۰ و قابلِ کشف |

**سناریوهای پذیرش** — همان ۹ سناریوی ChatGPT + این سه:
- حذفِ فرمِ پیگیری با پاسخِ موجود ← رد شود (N1).
- دو کاربرِ پذیرش هم‌زمان «شروعِ ویزیت» یک نوبت را بزنند ← یک مراجعه (N2).
- شرکتِ تازه با حوزهٔ مطب: از صفر تا اولین ویزیت بدونِ تماس با پلتفرم (W4.3).
